# 리뷰 대응 도우미 — 신고 기준 데이터 설계서

작성일 2026-10-02 · 데이터 버전 2026-10-02

## 1. 왜 코드와 분리하나

배달앱의 리뷰 정책과 신고 절차는 자주 바뀝니다. 정책 문구를 앱 코드 안에 넣어 두면 정책이 바뀔 때마다 코드를 고쳐야 하고, 어느 내용이 언제 확인된 것인지 알 수 없게 됩니다.

그래서 정책·체크리스트·유형·답변 템플릿을 **JSON 파일 4개**로 분리했습니다. 정책이 바뀌면 JSON만 고치고, 앱은 그 파일을 읽어서 보여 줍니다. 혜택on에서 최저임금이나 4대보험 요율 같은 법정 수치를 JSON으로 관리하는 방식과 같습니다.

## 2. 파일 구성

| 파일 | 내용 | 고치는 때 |
|---|---|---|
| `platforms.json` | 플랫폼별 신고·게시중단 절차, 신청 요건, 조치 불가 사유, 처리 방식, 출처, 확인일 | **정책이 바뀌었을 때** (가장 자주) |
| `checklist.json` | 신고 전 체크리스트 8개 문항과 그 근거 조항 | 정책이 바뀌었거나 문구를 다듬을 때 |
| `types.json` | 리뷰 유형 15개, 분류 키워드, 신고 대상 표시 문구, 분석 결과 문구 | 키워드를 시험해 보고 고칠 때 |
| `templates.json` | 유형별 답변 템플릿 45개(15개 유형 × 3가지 말투), 빈칸 목록 | 문구를 다듬을 때 |
| `abuse-words.json` | **욕설·모욕 표현 사전** (44개 항목, 초안): 단어, 변형 표기, 사람 대상 조건, 오탐 방지 제외어 | 오탐·누락을 발견했을 때 |
| `abuse-tests.json` | 사전 시험 문장 36개(걸려야 하는 16개 + 걸리면 안 되는 20개) | 사전을 고칠 때 문장도 함께 추가 |
| `abuse_check.py` | 사전 규칙을 코드로 옮긴 **참고 구현**. 개발 도구가 앱을 만들 때 이 동작을 기준으로 삼음 | 규칙을 바꿀 때 |
| `classify-fixtures.json` | **리뷰 유형 분류 시험 문장 81개**(대표 유형·보조 유형·욕설 감지 기대값). 칭찬 문장이 불만 유형으로 잘못 분류되지 않는지, 받침 변형(맛잇다·늦엇어요)·일반 불만 표현·칭찬 보호도 포함 | 키워드를 고칠 때 문장도 함께 추가 |
| `normalize-fixtures.json` | 분류 매칭용 **표기 정규화 시험 41개**(입력·기대 결과). Python·JS 구현이 모두 같은 결과여야 함 | 정규화 규칙을 바꿀 때 |
| `classify_check.py` | 유형 분류 규칙(`types.json`의 `classification.steps`)과 표기 정규화(`normalize_for_match`)를 코드로 옮긴 **참고 구현** | 분류 규칙을 바꿀 때 |
| `validate.py` | 위 파일들이 서로 맞게 연결되어 있는지, 확인일이 오래되지 않았는지, 욕설 사전 시험이 통과하는지 점검 | JSON을 고친 뒤 배포 전에 |

**폴더 위치 제안:** 혜택on 저장소의 `data/review-helper/` 아래에 4개 JSON을 두고, 도구 페이지(`pages/tools/review-helper/`)에서 읽습니다.

## 3. 핵심 필드 설명

### platforms.json

| 필드 | 뜻 |
|---|---|
| `staleAfterDays` | 확인일이 이 일수(기본 90일)를 넘으면 앱이 "정책이 바뀌었을 수 있어요"를 표시 |
| `platforms[].inScope` | 1차 범위 여부. 네이버는 `false`(공식 원문 미확인) |
| `policy.versionLabel / effectiveDate` | 확인한 정책의 판과 시행일 |
| `policy.verifiedDate` | 공식 원문을 마지막으로 확인한 날짜 |
| `policy.verification` | 확인 방법: `official_pdf` · `official_web` · `app_capture` · `secondary`(기사·블로그) |
| `policy.confidence` | `high`(공식 원문 확인) · `medium` · `low`(2차 자료만) |
| `policy.officialUrl / officialUrlNote` | 공식 링크가 있으면 링크, 없으면(배민) 안내 문구를 표시 |
| `request.channels` | 신청 경로(전화·이메일 등). `verifiedOfficial`이 `false`이면 2차 자료 기준 |
| `request.requirements` | 신청 요건. 항목마다 근거 조항(`article`) 포함 |
| `request.notAccepted.strength` | 조치 제외 사유의 세기: `mandatory`(조치하지 않습니다) · `principle`(원칙적으로, 예외 있음) · `may`(않을 수 있습니다) |
| `request.process` | 임시조치 일수, 작성자 이의 처리, 재요청 가능 여부, 총점 제외 여부 |
| `sources` | 출처 목록. 공식 원문과 기사·블로그를 구분 |
| `openQuestions` | 아직 확인하지 못한 항목 |

`strength`가 중요한 이유: 세 플랫폼의 표현이 서로 다릅니다. 쿠팡이츠는 "조치하지 않습니다", 배민은 "원칙적으로 … 다만 충분히 소명하면 가능", 요기요는 "않을 수 있습니다"입니다. 앱 문구에 "원칙적으로"를 붙이는 이유가 이것입니다.

### checklist.json

- `items[].text`: 앱 화면에 보여 줄 문구.
- `items[].basis[]`: 이 문항이 어느 플랫폼의 어느 조항에 근거하는지. `verified`가 `false`이면 공식 원문으로 확인하지 못한 항목입니다.
- `wordingRules`: 문구를 쓸 때 지킬 규칙("허위·거짓 같은 단정 표현 금지" 등).

### types.json

- `classification.steps`: **유형을 고르는 순서**(짧은 글은 욕설·키워드가 하나도 없을 때만 별점만, 일반 불만 표현만 있으면 미분류 → 위험·핵심 유형 우선 → 칭찬+불만 혼합 → 일반 불만). `priority` 숫자는 같은 단계 안에서만 쓴다.
- `match`: 분류 방법. `keywords`(키워드 포함) · `short_text`(글자 수 짧음) · `dictionary`(`abuse-words.json` 사전, 욕설·비방 유형) · `mixed`(칭찬+아쉬움).
- `priority`: 여러 유형이 걸릴 때 숫자가 작은 유형을 대표로 사용.
- `reportStatus`: 신고 대상 표시. `reportStatuses`에서 문구를 찾습니다.
  - `not_target` 신고대상은 아닙니다. · `principle_not_target` 원칙적으로 신고대상은 아닙니다. · `check_first` 상황부터 확인하세요. · `verify_records` 주문 기록을 확인한 뒤에 판단하세요. · `may_review` 신고 검토가 가능할 수 있어요. · `not_applicable` 해당 없음
- `caution`: `true`이면 안내 상자를 주황색으로 표시(이물질·위생, 욕설·비방, 사실 확인).
- `result`: 분석 결과 화면에 쓰는 제목, 태그, 조언, 이유, 확인해 볼 점, 다음 단계.
- `replyBanner`: 답변 초안 화면의 한 줄 안내.
- `classification.generalNegative`: 특정 유형이 없는 일반 불만 표현(최악·실망·비추천·안 좋…). 이것만 걸리면 짧은 글이라도 '별점만'(T11)이 아니라 **미분류**로 돌려 사장님이 유형을 고르게 한다.
- `classification.positiveGuards`: 칭찬 키워드가 부정 표현의 일부일 때 칭찬으로 세지 않는 규칙(아래 표). 막힌 칭찬은 일반 불만 표현으로 본다.

**키워드 비교 방식 (표기 정규화).** 키워드는 사람이 읽기 좋게 표준 표기로 적는다. 분류할 때 리뷰 글과 키워드를 모두 같은 규칙으로 바꾼 뒤 부분일치로 비교하므로 띄어쓰기·받침 변형은 따로 적지 않아도 된다.
① 소문자·NFC ② 공백 모두 제거("맛 없어요"→"맛없어요") ③ 받침만 접기 ㅆ→ㅅ, ㄲ·ㄳ→ㄱ, ㅄ→ㅂ, ㄶ→ㄴ, ㅀ→ㄹ("맛있다"·"맛잇다" 모두 같은 글자로). ㅎ 받침 삭제와 ㅐ/ㅔ 접기는 하지 않으므로 "조아요"처럼 이 규칙으로 못 잡는 표기는 키워드로 직접 적는다. 욕설 사전에는 이 규칙을 쓰지 않는다.

**칭찬 키워드 보호 규칙 (positiveGuards)** — 정규화한 글자 기준

| 구분 | 키워드 | 막는 조건 | 예 |
|---|---|---|---|
| 앞 글자 | 만족 | 바로 앞이 불·미 | 불만족 |
| 앞 글자 | 추천 | 바로 앞이 비 | 비추천 |
| 앞 글자 | 맛있·좋아요·좋았·좋다·좋아·좋네·좋은·좋습 | 바로 앞이 안·못 | 안좋아요, 안 맛있어요 |
| 뒤 표현 | 칭찬 키워드 전부 | 키워드 끝에서 6자 이내에 지않·진않·지안·지못·의사없·의향없·안할·안시·안먹 | 맛있지 않아요, 재주문 의사 없음 |

- 표에 없는 키워드에는 앞 글자 보호가 없다("불맛있어요"는 칭찬 그대로).
- "친절"은 칭찬 키워드에 넣지 않는다. "불친절"(응대 불만 T09) 안에 "친절"이 있어 혼합 리뷰로 잘못 분류되기 때문이다.
- **보호 규칙을 더 늘리기 전에 사용자 확인을 받는다.** 막는 조건이 늘수록 정상 칭찬이 칭찬으로 안 잡힐 수 있다.

### templates.json

- `templates[]`: 유형 ID별 `polite` · `short` · `sincere` 3가지 말투.
- `blanks[]`: `[가게 이름]` 같은 빈칸의 의미, 예시, 필수 여부. `[가게 이름]`은 확인 화면의 가게 이름 입력칸 값으로 자동 채웁니다.

### abuse-words.json (욕설·모욕 표현 사전)

단어 목록만 쓰면 "존맛", "시발점", "앱이 꺼져요" 같은 정상 문장이 욕설로 잡힙니다. 그래서 단어와 함께 **오탐을 막는 규칙**을 넣었습니다.

| 구분 | 설명 | 예 |
|---|---|---|
| 욕설 (severity 3) | 그 자체로 욕설. 찾으면 곧바로 "신고 검토 안내" 대상 | 직접 욕설, 변형 표기(점·숫자 끼워 넣기, 초성) |
| 모욕 (severity 2) | **사람을 가리키는 말이 근처에 있을 때만** 센다 | "사장 ○○"은 모욕, "음식이 ○○ 같아요"는 맛 평가라 제외 |
| 문맥 모욕 (severity 1, 승격) | 사람 대상일 때만 모욕으로 승격 | "새끼"는 "사장 새끼"만, "새끼손가락"·"새끼 고양이"는 제외 |
| 저주·협박 (severity 3) | 사람 대상 여부와 상관없이 센다 | "망해라", "가만 안 둔다" 등 |
| 거친 표현 (severity 1) | **태그만** 붙이고 신고 검토 안내에는 쓰지 않음 | "존나", "미친 맛" 같은 칭찬에도 쓰이는 말 |

- `exclusions`: 오탐을 막는 낱말(시발점, 병신년, 쓰레기통, 도둑맞…).
- `notInDictionaryOnPurpose`: 일부러 뺀 단어와 이유("꺼져", "닥치고", "씹", "돼지" 등).
- `personTargets` / `personWindowChars`: 사람을 가리키는 말(사장, 직원, 라이더…)과 확인할 글자 범위(앞뒤 10자).
- 이 사전은 **혐오·차별 표현(성별·국적·장애·지역 등)은 포함하지 않습니다.** 필요하면 별도 사전으로 만들어야 합니다.

**사전을 고치는 방법**
1. 못 잡은 욕설이 있으면 `entries`에 항목을 추가하고, 그 문장을 `abuse-tests.json`의 `expectAbusive: true` 시험 문장으로 추가합니다.
2. 정상 문장이 잡히면 `exclusions`에 그 낱말을 추가하거나 항목의 조건을 좁히고, 그 문장을 `expectAbusive: false` 시험 문장으로 추가합니다.
3. `python validate.py`를 실행해 시험이 모두 통과하는지 확인합니다.

## 4. 앱이 데이터를 쓰는 방식

| 화면 | 읽는 데이터 |
|---|---|
| 확인 화면 | `platforms.json`의 플랫폼 이름 목록 |
| 분석 결과 | `types.json`에서 유형을 찾아 제목·신고 문구·이유·확인할 점 표시 |
| 관련 플랫폼 정책 | 선택한 플랫폼의 `policy.versionLabel`, `verifiedDate`, 공식 링크 |
| 답변 초안 | `templates.json`에서 유형·말투에 맞는 템플릿, `types.json`의 `replyBanner` |
| 신고 전 체크리스트 | `checklist.json` 문항 + 선택한 플랫폼의 `basis` |

**표시 규칙**
1. 플랫폼 정책 카드에는 시행일과 확인일을 항상 함께 보여 줍니다.
2. `confidence`가 `low`이거나 확인일이 `staleAfterDays`를 넘으면 "정책이 바뀌었을 수 있어요. 공식 안내를 확인하세요"를 표시합니다.
3. 모든 결과 화면에 `disclaimer`("참고용 안내이며, 최종 판단은 각 플랫폼 정책에 따라요.")를 표시합니다.
4. `not_target`은 욕설·비방·개인정보 키워드가 감지되지 않을 때만 사용합니다.
5. 자동 분류가 틀릴 수 있으므로 사장님이 유형을 바꿀 수 있어야 하고, 바꾸면 신고 문구와 답변 초안도 함께 바뀌어야 합니다.

## 5. 정책이 바뀌었을 때 고치는 순서

1. 해당 플랫폼의 공식 정책을 다시 열어 바뀐 조항을 확인합니다.
2. `platforms.json`에서 그 플랫폼의 `policy.versionLabel`, `effectiveDate`, `verifiedDate`를 고치고, 바뀐 조항은 `request`와 `notAccepted`에서 고칩니다.
3. 그 조항을 근거로 쓰는 문항이 있으면 `checklist.json`의 `basis.ref`와 문구를 고칩니다.
4. 맨 위 `dataVersion`을 오늘 날짜로 바꾸고 `changelog`에 한 줄 적습니다.
5. `python validate.py`를 실행해 "통과"가 나오는지 확인합니다.

## 6. 출시 전 점검

- [ ] `python validate.py`가 "통과"인가
- [ ] 플랫폼마다 `verifiedDate`가 90일 안인가
- [ ] 요기요 정책이 2023-10-04 이후 개정되지 않았는지 확인했는가
- [ ] 배민 신청 화면의 입력 항목(가게번호·리뷰번호 등)을 공식 안내로 확인했는가
- [ ] 실제 리뷰 20~30건으로 분류 키워드를 시험했는가
- [x] 욕설·모욕 표현 사전(`abuse-words.json`) 초안 작성, 시험 문장 36개 통과
- [ ] 욕설 사전을 실제 리뷰 20~30건에 적용해 오탐·누락을 확인했는가
- [ ] 혐오·차별 표현이 필요한지 정했는가 (현재 사전에서 제외)
- [ ] 템플릿 문구를 사장님이 읽고 가게 말투에 맞게 고쳤는가

## 7. 아직 확인하지 못한 것

## 8. 개발 도구에 전달할 요청문 (복사해서 사용)

> 혜택on 저장소의 `data/review-helper/`에 있는 JSON 4개(`platforms.json`, `checklist.json`, `types.json`, `templates.json`)를 읽어서 동작하는 모바일 우선 반응형 웹 도구를 `pages/tools/review-helper/`에 만들어 주세요.
>
> 규칙:
> 1. 정책 문구, 체크리스트, 신고 문구, 답변 템플릿은 코드에 직접 쓰지 말고 JSON에서 읽어 주세요.
> 2. 플랫폼 정책 카드에는 `policy.versionLabel`, `effectiveDate`, `verifiedDate`를 항상 표시하고, `officialUrl`이 있으면 링크로, 없으면 `officialUrlNote`를 표시해 주세요.
> 3. `policy.confidence`가 `low`이거나 `verifiedDate`로부터 `staleAfterDays`가 지났으면 "정책이 바뀌었을 수 있어요. 공식 안내를 확인하세요"를 표시해 주세요.
> 4. 유형은 `types.json`의 `match` 규칙과 `priority`로 자동 분류하되, 사장님이 직접 바꿀 수 있어야 하고 바꾸면 신고 문구와 답변 초안이 함께 바뀌어야 합니다.
> 5. `reportStatus`의 `tone`이 `caution`이면 주황색 안내 상자로 표시해 주세요.
> 6. 모든 결과 화면에 `disclaimer`를 표시해 주세요. "허위", "거짓" 같은 단정 표현은 어디에도 쓰지 마세요.
> 7. 답변 초안의 `[가게 이름]` 같은 빈칸은 노란색으로 강조하고, 사용자가 입력하면 채워지게 해 주세요. 복사 버튼을 두어 주세요.
> 8. 로그인과 서버 저장 없이 동작해야 하며, 리뷰 내용은 서버로 보내지 않습니다.
> 9. `inScope`가 `false`인 플랫폼(네이버)을 고르면 "확인 중인 정보예요"를 표시해 주세요.
> 11. 하단 탭은 '무료도구 돌아가기'(두 줄 표기)(혜택on 무료도구 허브로 이동) · '기록' · '통계' 3개입니다. 기록·통계는 '준비중' 배지를 달고, 누르면 "준비 중이에요. 곧 만나요." 안내만 보여 주세요. 두 탭의 클릭을 GA4 이벤트로 기록해 주세요.
> 12. 초기화: 입력 화면에 '지우기'(입력한 리뷰 삭제), 결과·답변 화면에 '처음부터 다시하기'(리뷰·선택한 유형·말투·빈칸 입력을 모두 처음 상태로)를 두어 주세요. 모바일과 PC 모두 같은 이름을 씁니다.
> 10. 유형 T12(욕설·비방) 분류는 `abuse-words.json`을 `abuse_check.py`와 같은 규칙으로 구현해 주세요. `abuse-tests.json`의 문장 36개가 모두 같은 결과로 나와야 합니다. 욕설 단어는 화면에 다시 출력하지 마세요.
